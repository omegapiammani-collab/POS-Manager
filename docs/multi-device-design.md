# แผนตัดสินใจระบบ POS หลายอุปกรณ์

เอกสารนี้ใช้วางแผน ยังไม่ได้เลือกผู้ให้บริการ เปิดเครือข่าย หรือเพิ่มบัญชีผู้ใช้ เป้าหมายคือเจ้าของร้านคนเดียวใช้คอมพิวเตอร์ มือถือ และแท็บเล็ต ขายออฟไลน์แล้วซิงก์เมื่อเชื่อมต่อได้ โดยไม่ทิ้งบิลและแจ้งสต็อกติดลบ ต้องตรวจค่าใช้จ่ายและข้อจำกัดของทางเลือกจริงก่อนยืนยันว่าใช้งานฟรีได้ต่อเนื่อง

## ข้อเท็จจริงจากโค้ดปัจจุบัน

- `inventory_api.py` ฟังที่ `127.0.0.1` และตรวจ Host ให้เป็น `localhost` หรือ `127.0.0.1` พร้อมพอร์ตเซิร์ฟเวอร์ มือถือเครื่องอื่นจึงยังเชื่อมต่อฐานนี้โดยตรงไม่ได้
- หน้าขายเก็บบิลค้างใน IndexedDB ของแต่ละ browser profile และส่งบิลด้วย ID เดิมเมื่อเชื่อมต่อได้ ฐานข้อมูลตรวจ ID ซ้ำในธุรกรรมและรองรับการบันทึกยอดขายออฟไลน์พร้อมแจ้งสต็อกขาด
- `binding_id` ใช้ตรวจว่าคำขอและฐานข้อมูลตรงกัน ไม่ใช่บัญชี รหัสผ่าน หรือการยืนยันสิทธิ์ เจ้าของร้านจึงยังไม่สามารถใช้ค่านี้เป็นกุญแจเข้าระบบจากเครือข่าย
- ระบบปัจจุบันใช้ service worker และ Web Locks ในหน้าขาย สิ่งเหล่านี้ต้องตรวจการรองรับและ secure context บนเบราว์เซอร์อุปกรณ์เป้าหมายจริง ไม่ใช่เพียงจำลองหลาย profile
- SQLite เป็นฐานข้อมูลฝั่งเซิร์ฟเวอร์เดียว ไฟล์สำรองฐานไม่รวมคิวที่ยังอยู่ในเบราว์เซอร์แต่ละเครื่อง การกู้ฐานเก่าอาจขาดบิลหรือการยกเลิกหลังเวลาสำรอง

## ข้อมูลที่ยังต้องตัดสินใจ

1. ยืนยันแล้ว: ต้องเข้าใช้งานจากนอกเครือข่าย Wi-Fi ของร้านผ่านอินเทอร์เน็ตได้
2. คอมพิวเตอร์หลักต้องเปิดอยู่เสมอหรือยอมรับเซิร์ฟเวอร์ออนไลน์ได้ การปิดเครื่องหลักจะกระทบเวลาซิงก์อย่างไร
3. ใครเป็นผู้ดูแลบัญชีและกู้คืนเมื่อเปลี่ยนเครื่อง ทำมือถือหาย หรือลืมข้อมูลเข้าระบบ
4. ข้อมูลลูกค้าและข้อมูลขายจะเก็บที่ไหน ข้อกำหนดสำรอง ระยะเวลาเก็บ และการเข้าถึงข้อมูลเป็นอย่างไร
5. ค่าใช้จ่าย ข้อจำกัดจำนวนอุปกรณ์ พื้นที่ การโอนข้อมูล และเงื่อนไขของบริการที่เสนอเป็นเท่าใด และเปลี่ยนแปลงได้อย่างไร

## ทางเลือกเพื่อพิจารณา

| แนวทาง | สิ่งที่ต้องเพิ่ม | ข้อแลกเปลี่ยนที่ต้องตรวจ |
| --- | --- | --- |
| เครื่องหลักในร้านเป็นเซิร์ฟเวอร์ | ช่องทาง HTTPS ที่อุปกรณ์เชื่อถือได้ การจับคู่อุปกรณ์และสิทธิ์เจ้าของ การสำรองข้อมูล | ต้องเข้าถึงเครื่องหลักและเปิดเครื่องไว้เมื่อซิงก์; การออกและต่ออายุใบรับรองกับการค้นหาเครื่องต้องออกแบบ |
| เครื่องหลักร่วมกับช่องทางส่วนตัว | การจับคู่อุปกรณ์ HTTPS การจัดการสิทธิ์และการเพิกถอน พร้อมทดสอบช่องทางที่เลือก | ขึ้นกับบริการหรือเครือข่ายส่วนตัวและสถานะเครื่องหลัก; ตรวจต้นทุน ข้อจำกัด และวิธีกู้คืนก่อนเลือก |
| เซิร์ฟเวอร์กลาง | ตัวตนเจ้าของ การลงทะเบียน/เพิกถอนอุปกรณ์ HTTPS ที่จัดการได้ ฐานข้อมูลและการสำรองฝั่งเซิร์ฟเวอร์ | เพิ่มงานดูแลและความเสี่ยงจากการเปิดบริการ; ต้องตรวจโควตา ค่าใช้จ่ายและการนำข้อมูลออก |

ทุกแนวทางต้องถือว่าเครื่องของเจ้าของแต่ละเครื่องอาจถูกขโมยหรือเปลี่ยนเครื่องได้ และต้องไม่ถือว่าการรู้ URL หรือ `binding_id` เท่ากับได้รับอนุญาต

## ลำดับงานหลังเลือกแนวทาง

1. ระบุขอบเขตเครือข่ายและแบบตัวตนเจ้าของ/อุปกรณ์ รวมการเข้าร่วม เพิกถอน หมดอายุ และกู้คืน โดยไม่เก็บความลับในคิวสำรองหรือ log
2. ออกแบบ TLS, origin, การป้องกันคำขอข้ามเว็บไซต์, การจำกัดสิทธิ์ทุก endpoint รวมการดาวน์โหลดฐาน และนโยบายไม่เปิดบริการสาธารณะโดยปริยาย
3. ระบุแหล่งข้อมูลหลักหนึ่งแห่งและโปรโตคอลซิงก์: ID บิลคงเดิมเมื่อ retry, จัดการผลตอบกลับสูญหายและ ID ชนกัน, ตรวจ binding ก่อนเขียน และเก็บรายการที่ตัดสินใจไม่ได้ให้ตรวจด้วยตนเอง
4. วางแผนกู้ฐานและคิวจากทุกเครื่อง รวมการตรวจประวัติภายนอกหลัง restore ฐานเก่า และขั้นตอนสำรองก่อนเปลี่ยนรุ่น
5. สร้างต้นแบบในสภาพแวดล้อมแยก ทดสอบก่อนให้เจ้าของอนุมัติการเชื่อมต่อจริงหรือ deploy

## เกณฑ์ทดสอบก่อนใช้งานจริง

- เข้าระบบและเพิกถอนอุปกรณ์ได้ อุปกรณ์ที่ไม่มีสิทธิ์อ่านหรือเขียน รวมถึงดาวน์โหลดฐานไม่ได้; การโจมตีข้าม origin ไม่สามารถเปลี่ยนข้อมูลได้
- ทดสอบคอมพิวเตอร์ มือถือ และแท็บเล็ตจริงในเบราว์เซอร์ที่รองรับ HTTPS, service worker และ Web Locks ทั้งเปิดออนไลน์ครั้งแรก ปิด/เปิดใหม่ และออฟไลน์
- สองเครื่องขายสินค้าชิ้นสุดท้ายพร้อมกันโดยออฟไลน์ แล้วกลับมาออนไลน์ต่างลำดับ: บิลทุกใบอยู่ครบ ไม่หักซ้ำ มีรายการสต็อกติดลบ และบันทึกการรับสินค้าล้างยอดขาดได้
- จำลองการส่งซ้ำ การตอบกลับหาย การปิดแท็บระหว่างซิงก์ การหมดอายุสิทธิ์ และ server restart: คิวที่ยังไม่ยืนยันต้องไม่หาย และไม่มีบิลซ้ำ
- กู้ฐานที่เก่ากว่าบิลค้าง พร้อมสำรองคิวทุกเครื่อง: ระบบไม่ส่งรายการที่ต้องตรวจโดยอัตโนมัติ และเจ้าของตรวจประวัติภายนอกก่อนตัดสินใจได้
- ตรวจการสำรอง/กู้คืน การเพิกถอนเครื่องสูญหาย และต้นทุนจริงของตัวเลือกที่เลือก ทั้งในภาวะเครือข่ายปกติและขัดข้อง

การทดสอบข้างต้นเป็นเป้าหมาย ไม่ใช่ผลทดสอบที่ผ่านแล้ว และไม่ได้รับรองความพร้อมใช้งานหลายอุปกรณ์ใน production
