# การทดลองขอบเขตเจ้าของร้าน

นี่เป็นการทดลองในหน่วยความจำเพื่อทดสอบจุดตัดสินสิทธิ์ ไม่ใช่ระบบล็อกอิน ไม่มีการเชื่อมกับ `inventory_api.py`, HTTP server, Cloudflare หรือ Supabase และห้ามใช้เปิดรับคำขอจากอินเทอร์เน็ต

## สิ่งที่ทดลอง

`owner_boundary.py` ให้ pipeline จำลองส่งคำขอ GET/POST ทุก path ผ่าน policy ก่อน backend จำลอง โดยต้องได้ `VerifiedIdentity` จาก verifier ฝั่งเซิร์ฟเวอร์ที่เชื่อถือได้ และตรวจ issuer, subject, audience และเวลาหมดอายุเทียบค่าที่กำหนด การเขียนต้องมี Origin ที่ตรงกับ HTTPS origin ที่กำหนด; Origin ที่มีแต่ไม่ตรงถูกปฏิเสธทั้งอ่านและเขียน การทดลองรับ bearer token หนึ่งค่าจาก `Authorization` และไม่ใช้ email, `X-Forwarded-User` หรือ `X-POS-Store-ID` เป็นตัวตน

เทสต์ใช้ verifier ปลอมเท่านั้น ผลผ่านไม่ได้พิสูจน์ว่าลายเซ็น token ถูกตรวจ หรือป้องกันผู้โจมตีจริง verifier จริงต้องตรวจลายเซ็นและ claims ด้วย SDK/ไลบรารีที่ดูแลแล้ว ใช้แหล่งกุญแจที่เชื่อถือได้ ตรวจการหมุนกุญแจและความพร้อมใช้งาน และกำหนดนโยบายยกเลิก session การทดสอบ pipeline นี้ไม่ใช่ทางเลือกแทนสิ่งเหล่านั้น

## ทางเลือกที่ยังไม่ตัดสินใจ

- Cloudflare Access สามารถเป็นตัวกลางยืนยันตัวตนได้ แต่ backend ที่เกี่ยวข้องยังต้องตรวจหลักฐานตามรูปแบบ deployment ที่เลือก และต้องป้องกันการข้ามตัวกลาง: [Cloudflare: Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/). การนำ local server ปัจจุบันไปเปิดผ่าน tunnel โดยยังไม่มีการตรวจสิทธิ์ที่ปลอดภัยไม่อยู่ในขอบเขตการทดลองนี้
- Supabase Auth เป็นอีกแนวทางสำหรับตัวตน โดยเอกสารแนะนำ `getClaims()` หรือไลบรารีตรวจ JWT ที่มีคุณภาพ แทนการเขียนตัวตรวจลายเซ็นเอง: [Supabase: JWT](https://supabase.com/docs/guides/auth/jwts). การใช้ฐานข้อมูลหรือ API ของบริการต้องออกแบบการจำกัดสิทธิ์ทุกตารางและ endpoint แยกต่างหาก
- ทั้งสองทางเลือกมีเงื่อนไขและโควตาที่เปลี่ยนได้ ยังไม่ได้ยืนยันว่าใช้งานร้านจริงได้ต่อเนื่องด้วยค่าใช้จ่าย 0 บาท ตัวอย่างเช่น [Supabase ระบุว่าโปรเจกต์ฟรีอาจถูกพักเมื่อกิจกรรมน้อย](https://supabase.com/docs/guides/platform/free-project-pausing) ต้องตรวจราคา โควตา การสำรองและการกู้คืน ณ วันที่เลือกใช้ รวมค่าอุปกรณ์และอินเทอร์เน็ตตามขอบเขตที่เจ้าของร้านกำหนด

## งานจำเป็นก่อนเชื่อมระบบจริง

1. เลือกผู้ให้บริการและแบบการระบุตัวเจ้าของที่กู้คืนและเพิกถอนอุปกรณ์ได้ โดยไม่ใช้ข้อมูลโปรไฟล์ที่ผู้ใช้แก้เองเป็นสิทธิ์
2. ใช้ verifier ของผู้ให้บริการหรือไลบรารีที่เหมาะสม พร้อมทดสอบ token ปลอม หมดอายุ ผิด issuer/audience การหมุนกุญแจ การถอนสิทธิ์และกรณี verifier ใช้งานไม่ได้
3. ออกแบบ session, HTTPS, CORS/CSRF, การป้องกัน origin bypass และการควบคุมสิทธิ์ทุก endpoint รวมทั้ง asset, API และไฟล์สำรอง โดยไม่บันทึก token ลง log หรือไฟล์สำรอง
4. ทดสอบ integration กับ server และฐานข้อมูลจำลองที่แยกจากข้อมูลจริงบนอุปกรณ์หลายเครื่อง รวมการขายออฟไลน์ บิลซ้ำ สต็อกติดลบ การกู้ฐานเก่า และการเพิกถอนเครื่อง
5. ตรวจโควตา ต้นทุน ข้อตกลงการเก็บข้อมูล และกระบวนการกู้คืนก่อนนำเสนอให้เจ้าของอนุมัติการติดตั้งจริง

`OwnerPolicy` และ `VerifiedIdentity` เป็นโครงสร้างทดสอบ ไม่ใช่สัญญาว่าจะใช้รูปแบบ token หรือ provider ใด และไม่มีการตั้งค่าเริ่มต้นที่เปิดการเข้าถึง
